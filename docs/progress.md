## 3. M5（辞書の解決規則）で決めたこと

詳しい仕様は[計画の 3.1 節](plan.md#31-辞書の解決規則m5)にあります。

- ソースと同じディレクトリから設定ファイルのディレクトリまで探索し、最も近い `terms.yaml` だけを使う。親や兄弟の辞書とはマージしない
- ルートの辞書は任意。コンテキストごとに同名の用語を別の意味・振る舞いで定義できる。空の辞書も境界になる
- ルールの `include` に一致するソースに辞書がなければ、ソースのディレクトリごとに 1 回だけエラー。不正・読み取り不能な辞書から親へはフォールバックせず、同じ辞書の問題は 1 回だけ報告する。重複抑制は `Reporter` が管理する。他のコンテキストの検査は続ける。ルール対象外のソースには辞書を要求しないが、読み込み・構文エラーは報告する
- `--dictionary` は従来どおり、カレントディレクトリからのパスで全ソースに同じ辞書を適用し、自動解決を無効にする
- 辞書はソースの依存定義なので、辞書ファイル名そのものへの ignore/exclude では境界を消さない。ルート以外ではルール対象のパスから参照される辞書だけ先読みし、ソースの読み込み・構文エラーがあればそのソースに対応する辞書エラーは報告しない
- シンボリックリンクは探索時の見えるパスで辞書を選ぶ。リンク先のパスへは切り替えない
- コアの `resolution` モジュールに `DictionaryResolver` を追加。辞書・不存在・失敗のキャッシュは検査 1 回限りとし、再検査時には作り直す。CLI は解決後に `loaded_dictionary` で共有参照し、`Checker` と索引を辞書のパスごとに使い回す
- 用語追加のヒントと、外側の型が辞書にない診断には、適用した辞書のパスを含める
- `examples/order-service` はルート辞書をパッケージ配下に移し、注文と請求の 2 つの辞書を解決するサンプルに更新した
- 共有辞書の取り込み・合成は未実装。暗黙の継承はせず、明示的な参照のスキーマは今後検討する

## 4. M4 から引き継いだ判定・探索の仕様

- M4 で決めたこと:
  - 検査するファイルは設定ファイルのディレクトリ以下。`.gitignore`・`.ignore`・隠しファイル（`.git` など）は尊重し（リポジトリ内では git と同じ境界でリポジトリ外の `.gitignore` は使わず、tarball 等のリポジトリ外ではツリー内のものだけ適用する）、シンボリックリンクは辿る。さらに設定ファイルの `exclude`（`include` と同じ glob 作法）に一致するファイルは一切読み込まない（ディレクトリを飛ばすのは `legacy/**` のように `/**` で終わる glob の手前部分に一致するときだけで、`src/*` のような glob はディレクトリ名には当てない）
  - `{any}` は空でない単語列にのみ一致する（`get{any}` は `get` だけには一致しない）
  - 同じ識別子に複数のルールが当たったときは、すべてのルールを満たす必要がある
  - 違反メッセージの「最も近いパターン」は動詞チェックだけ緩めた照合で選ぶ。緩めた照合では `{verb}` は 1 語か既知の活用形に一致する単語列しか取らない（`updateOrder` は `{verb}{noun}` への `update` 違反として報告され、`OrderShippingAddress` はパターン一覧のメッセージになる）
  - 定義済みだが活用形の違う動詞は、その振る舞いが期待する形だけを示す（「`{verb:pp}` expects `placed`」の形）
  - 「新しい用語・振る舞いなら辞書に定義する」というヒントは、パターンに `{noun}` か `{verb}` を含むルールにだけ出す（`get` を辞書に定義しても `get{any}` には一致しないため）。M5 で実際に適用した辞書のパスも表示するようにした
  - 空の単語列に分割される識別子（`__` など）はヒントなしの専用メッセージ（「単語を含まない」旨）で違反報告する
  - `{verb}` を結び付ける外側の型は最も内側の名前付きの型（無名クラスは飛ばし、辞書にない名前付きの型は飛ばさない）。後者の場合、結び付けができないことをエラーメッセージで報告する
  - 識別子内に `{noun}` が複数あるときは、最初の `{noun}` の用語に `{verb}` を結び付ける
  - enum 定数と record コンポーネントは `target: field` の対象（plan §4 の target の説明もこれに合わせて更新済み）
  - 1 つのファイル内の違反は位置（行・列）でソートして出力する（シンボルの登録順はソース順と限らないため）
  - ソースファイルは UTF-8 のみを読み込む。非 UTF-8 のファイルは `cannot read the file` エラーとして報告し、他のファイルの検査は続ける。そのようなファイルは `exclude` で除外できる
  - 設定ファイルと、存在するルート辞書（または `--dictionary` の指定辞書）は両方読み込んでから、エラーをまとめて 1 回で報告する
  - ディレクトリ走査のエラーは失敗したパスを先頭にして報告して失敗させる。ただし `exclude` に一致するパスやソースでないファイル（例: リンク先が存在しないシンボリックリンクの README）のエラーは報告しない
  - 検査したソースファイルが 0 件のときは `warning: no source files were checked` を stderr に出す（「違反なし」と区別できるように）。警告は stdout の `path:line:col: error:` 行と混ぜず、終了コードにも影響しない（CI は違反のみで失敗）
  - 出力先のパイプが閉じられても（`| head` など）panic せず、終了コード 1 で終わる

## 5. M6 で実装したこと

- `ubiqlint.yaml` に任意の `import_rules` を追加しました。`id`・`include`・`internal_namespaces` で、対象パスと内部の名前空間を指定します。設定例と詳しい判定規則は[計画の 4.1 節](plan.md#41-インポート境界ルール)にあります
- 内部の名前空間と配下は許可します。外部から辞書の `terms[].name` と同じ名前を導入するインポートと、外部のワイルドカードインポートは違反です。名前と名前空間は大文字・小文字を区別し、`com.example.ordering` のように途中まで一致するだけの名前空間を内部とは扱いません
- static インポートも対象です。名前付きのものは最後の名前を検査し、型かメンバーかはクラスパスを使わずに区別できないため、辞書の用語と一致すれば報告します。完全修飾名での参照は許可します
- Java アダプタの返り値を `SourceFile { symbols, imports }` にしました。インポートの要素列は構文木から読み、コメントや空白を取り除きます。Unicode エスケープを変換して検査し、診断位置は書かれたままのソースを指します
- CLI は `Checker::check_file` で命名とインポートをまとめて検査し、位置順に報告します。構文エラーのあるファイルには境界検査をかけません。`exclude` と `--dictionary` は従来どおり有効です
- `examples/order-service` に設定と説明を加えました。設定の検証、境界の判定、Java の抽出、CLI の統合テストで動作を確認できます
- M5 の `DictionaryResolver` が解決した最も近い辞書を、命名とインポートの両方に使います。インポートルールだけが適用されるファイルも辞書を解決します。親・兄弟の辞書はマージせず、衝突の診断には適用した辞書のパスを含めます

## 6. M7 で実装したこと

詳しい仕様は[計画の 3.2 節](plan.md#32-辞書を編集するコマンドm7)にあります。

- CLI に `term add|edit|remove` と `behavior add|edit|remove` を追加しました。編集する辞書は `--dictionary` で指定し、省略するとカレントディレクトリの `terms.yaml` を編集します。辞書ファイルの新規作成と `context` の変更は扱いません（計画の 8 章に未決事項として追加）
- 語形は推測しません。単数形は `name` の単語列、`forms.base` は `verb` から自動で書き、ほかの語形はすべて引数で指定します。名前を変えて単数形が変わるときは `--plural`、動詞を変えるときは残りの 4 つの語形も必須です
- 引数の書式の誤りは clap の使い方のエラー（終了コード 2）、辞書と矛盾する編集はすべての問題をまとめて `path: error:` 形式で報告します（終了コード 1）。不正な辞書は `validate` と同じ診断を出して編集しません。いずれもファイルは変更しません。値が同じなら書き込まずに終了コード 0 で終わります
- コアに `edit` モジュールを追加しました。`edit::apply` は、モデル上で編集を検証してから、変更する行だけを YAML のテキストに反映します（手順を 1 つ反映するたびに YAML を読み直し、次の手順の位置を求めます）。最後に結果を辞書として読み直し、位置以外が期待した辞書と一致する場合だけ新しいテキストを返します。ファイルの読み書きは呼び出し側が行うので、M8 の MCP サーバからも使えます
- コメント・空行・書式・改行コード（CRLF）・BOM は、変更しない部分ではそのまま残ります。インデント、`forms` の書き方（フロースタイルか、1 行に 1 フィールドか）、要素間の空行は既存の要素に合わせます。行単位で書き換えられない書式（空でないフロースタイルの `terms` への追加など）は、書き換えずにエラーにします
- saphyr の位置は文字単位なので、バイト位置に変換して使います。ブロックコレクションの終端は次のトークンの位置になって行末コメントや空行を含むため、要素の終わりは子孫のスカラーの終わりから求めています
- CLI は同じディレクトリの一時ファイルに書いてから置き換えます。一時ファイルは `create_new` で排他的に作成し、既存のパスへは書き込まず、後始末でも自分が作ったファイルだけを消します。シンボリックリンクはリンク先を書き換え、パーミッションを保ちます
- `dictionary::validate_term_name` を公開し、辞書の読み込みと CLI の引数チェックで共有しています

## 7. M8・M9 で決めたこと

詳しい仕様は[計画の 6.1〜6.4 節](plan.md#61-共通層m8)にあります。

- **hooks には対応しない**: 当初の M8 にあった Claude Code の hooks との連携は外しました。hooks はエージェントごとに形式が違い、Claude Code の形式を読めるエージェントでも互換は部分的です。とくに、編集の後に結果をモデルに返す方法がエージェントによってばらつきます。編集のたびに違反を届ける役割は M9 の LSP サーバに任せ、hooks から使う場合に備えて、ファイルを指定する `check` と、主なエージェントの設定例だけを用意します
- **M8 の進め方**: 2 つの PR に分けます
  1. 検査の流れを CLI から新しい `ubiqlint-project` に移し、ファイルを指定する `check` を加える。CLI の既存のテストがそのまま通ることを確かめる
  2. `ubiqlint mcp` で起動する MCP サーバ（`ubiqlint-mcp`）と、導入手順・レビューの観点の文書を加える
- **MCP のツール**: `get_context`（辞書とルールの取得）、`check_code`（書き込む前の下書きの検査）、`check_files`（ディスク上のファイルの検査）と、M7 のコマンドに 1 対 1 で対応する 6 つの編集ツール（`add_term` など）です
- **MCP の実装**: MCP 2026-07-28 は `initialize` を廃止しており、旧来のクライアントは新しい版だけのサーバにつながりません。新旧両方の版を受け付けるため、公式の SDK である `rmcp` を使います。そのためにワークスペースの `rust-version` を 1.85 から 1.88 に上げます
- **MCP サーバの振る舞い**: 状態を持たず、呼び出すたびに設定と辞書を読み直します。設定ファイルは 1 つだけ扱い、既定はカレントディレクトリの `ubiqlint.yaml` です。出力は CLI と同じ行形式で、`check_files` は既定で 100 件までを返します。違反があってもツールとしては成功です。パスが範囲外、設定ファイルや辞書が不正、編集が拒否された、といった場合に `isError: true` にします
- **辞書の変更の判断**: 人の承認は挟みません。実装からレビューまでを AI エージェントが担う運用を想定し、違反を消すためだけの辞書の変更は、レビューするエージェントが `terms.yaml` の差分を見て止めます。MCP サーバの `instructions` でも、実装するエージェントにこの方針を伝えます
- **M9 の LSP サーバ**: 診断だけを扱います。`lsp-server` と `lsp-types` を使い、コアの `Diagnostic` に識別子の範囲とルール ID を加えます。着手する前に、Claude Code で `jdtls-lsp` と同じ `.java` に 2 つ目の LSP サーバを登録して、両方の診断が届くかを確かめます

## 8. M8 の 1 つめの PR で実装したこと

詳しい仕様は[計画の 6.1 節](plan.md#61-共通層m8)にあります。

- 新しい crate `ubiqlint-project` に、CLI の `check` にあった検査の流れを移しました。設定の読み込み（`Project::open`）、パスの変換（`Project::relative`）、ファイル探索（`Project::walk`）、アダプタの選択、1 ファイルの検査（`CheckRun::check`）、辞書の編集と書き込み（`edit_dictionary`、`replace_file`）です。CLI は結果の整形と、同じ問題を 1 回だけ報告する処理だけを受け持ちます
- `CheckRun::check` はファイルではなくテキストを受け取り、「検査しなかった（除外・未対応の言語）」「構文エラー」「どのルールも適用されない」「辞書がない」「辞書が不正」「検査した」を `FileReport` で区別して返します。MCP の `check_code` と LSP の未保存のバッファは、この関数を使う予定です
- コアの `DictionaryResolver::loaded_dictionary` が、辞書と一緒にそのパス（`ResolvedDictionary`）も返すようにしました。`CheckRun` が、resolver の持つパスを借りたまま `Checker` を使い回すためです
- `ubiqlint check [PATHS]...` で、検査するファイルやディレクトリを指定できるようにしました。直接指定したファイルには `.gitignore` を適用せず、`exclude` に一致するものや対応する言語のないものは警告して飛ばします
- 既存のテストは変更せずにすべて通ります（CLI から移した `replace_file` のテストだけは、新しい crate に移しました）。ファイルの指定について CLI のテストを 11 件、新しい crate の API とパスの変換について 14 件を追加しました（全 256 件）
- M5 の PR と同じ条件（5,000 用語、3,000 個のファイル）で、release ビルドを `main` と比べ、速度が落ちていないことを確かめました。途中で、ファイルの一覧を `BTreeSet` に入れ直す処理が数 ms 遅くしていたので、パスを指定しないときは探索結果をそのまま使うようにしています

## 9. M8 の 2 つめの PR で実装したこと

詳しい仕様は[計画の 6.2 節](plan.md#62-mcp-サーバm8)に、導入の手順は[エージェントとの連携](agents.md)にあります。

- 新しい crate `ubiqlint-mcp` と、それを起動する `ubiqlint mcp [--config <PATH>]` を追加しました。`get_context`・`check_code`・`check_files` と、M7 のコマンドに 1 対 1 で対応する 6 つの編集ツールを公開します
- 実装には `rmcp` 3.9 を使いました。MCP 2026-07-28 の `server/discover` と、2025-11-25 以前の `initialize` の両方に応じます。`rmcp` 3.x に合わせて `rust-version` を 1.88 に上げました。Rust 1.88 でもビルドとテストが通ることを確かめています
- `rust-version` を上げたことで、clippy が入れ子の `if let` を let チェーンにまとめるよう求めるようになったので、既存のコード（`config.rs` と `lexical.rs`）の入れ子の `if let` を let チェーンに書き換えました（振る舞いは同じです）
- サーバは起動時に設定ファイルのディレクトリへ移動し、パスをそこからの相対パスで受け取り、返します。ツールを呼ぶたびに設定と辞書を読み直し、状態を持ちません。辞書の編集はサーバの中で 1 つずつ処理します
- 結果は CLI と同じ行の形式で返します。そのために、問題の行の整形（`report` モジュール）と、指定したパスから検査するファイルを選ぶ処理（`Project::select`）を `ubiqlint-project` に移し、CLI と MCP サーバで共有しました。CLI の出力は変わっていません
- `check_files` は、どのルールも適用されないファイルを警告の行で示して「検査した」件数から外し、ルートの辞書を CLI と同じく必ず検証します（レビューでの指摘を受けて修正）
- クライアントがセッションを始める前に入力を閉じたとき（`server/discover` で確かめただけのときなど）、サーバがエラーで終わっていたのを、正常な終了として扱うようにしました
- テストでは、`ubiqlint mcp` を子プロセスとして起動し、標準入出力で新旧両方のやり取りを行います。ツールの説明・スキーマ・注釈は `tests/fixtures/mcp/tools.json` にスナップショットとして固定し、変えるときは `UBIQLINT_UPDATE_SNAPSHOTS=1` を付けてテストを実行します（全 273 件）
- [エージェントとの連携](agents.md)に、サーバの登録、Claude Code の権限設定、hooks から `check` を呼ぶ例、辞書の変更をレビューする観点をまとめました。hooks の設定例は、公式の文書で形式を確かめられた Claude Code のものだけを載せています
