# ubiqlint 構想

> 実装方針とマイルストーンは[実装計画](plan.md)にまとめています。

## 1. 背景と目的

### 1.1 背景

ドメイン駆動設計（DDD）におけるユビキタス言語は、チーム間の認識齟齬を排する強力な手法でありながら、運用の認知負荷が高く、人手による規律（ディシプリン）の維持が困難で形骸化しやすいという課題を抱えていた。

一方、コーディングエージェント（Claude Code、Devin 等）の台頭により、コード生成のボトルネックは「記述速度」から「ドメイン知識のセマンティック・ドリフト（意味のブレ）」へと移行している。エージェントは一般的な Web 上のコード学習データに引きずられ、ドメイン固有の概念を汎用的な CRUD 操作や安易な同義語で汚染しやすい。

### 1.2 目的

ユビキタス言語を「人間が遵守する努力目標」から「コーディングエージェントとコードベースを制御する厳密なプロトコル」へと昇華させる。

機械可読な辞書形式を定義し、静的解析・語形変化チェック・AI 連携を統合したリンターおよびエージェント向けツールチェーンを構築することで、ドメインモデルの整合性を自動検証・自律維持する。

## 2. コア設計原則

### 2.1 機能単位のコロケーション（Co-Location）

- プロジェクト全体で単一の巨大な辞書を抱えるのではなく、ドメイン境界・機能ディレクトリごとに分散配置する方式をサポートする（例: `src/.../order/terms.yaml`）。
- エージェントが必要な機能コンテキストのみを読み込めるため、LLM のトークン消費を最小化し、別コンテキストの同名単語による混同を物理的に遮断する。

### 2.2 振る舞い（動詞）のネスト定義

- 名詞（エンティティ・値オブジェクト）に対して、許容される操作（動詞）をネストして定義する。
- 定義されていない振る舞い（動詞）の使用を禁止し、ドメイン固有の表現（`place`、`cancel`、`publish` 等）を強制する。
- 過去分詞形をドメインイベント名（`OrderPlaced` 等）へマッピングし、イベント駆動の命名も同時に統一する。

### 2.3 語形変化の網羅（Exact Matching）

- 単数・複数形、動詞の活用形（現在・三人称単数・過去・過去分詞・動名詞）を辞書内に事前展開する。
- 形態素解析や NLP ライブラリの揺らぎ・例外バグを排除し、リンター側では完全一致判定（Exact Match）による高速・確実な静的検査を実現する。

### 2.4 外部ライブラリ・UI コンテキストとの境界保護

- ドメイン概念と外部 SDK / UI ライブラリの命名衝突（例: ドメインの `Item` と UI の `MenuItem`、Stripe SDK の `Customer`）を防ぐ。
- 外部ライブラリの汎用型に対してはエイリアスインポート（別名指定）や完全修飾などを強制し、ドメイン層へのセマンティック汚染を遮断する。

## 3. 辞書スキーマ仕様（YAML）

辞書ファイルは可読性、コメント記述性、複数行文字列への適応性、および LLM トークン効率の観点から YAML を採用する。

## 4. システムアーキテクチャ

コア部分は単一言語に依存させず、多言語展開、エージェント環境（MCP）を考慮したアーキテクチャを設計する。
