# ubiqlint 実装計画

この文書は、ubiqlint の実装方針とマイルストーンを記録するものです。背景・目的・設計原則は[構想文書](concept.md)にまとめており、ここではそれを実装に落とすにあたって決めたことを書きます。

ubiqlint は、ユビキタス言語を「人間が守るよう努める約束事」から「コーディングエージェントとコードベースを機械的に縛るルール」に変えるためのリンターです。機械可読な辞書を用意し、コード中の識別子が辞書に沿っているかを静的に検査します。

## 1. 決定事項

| 項目 | 決定内容 |
|---|---|
| 実装言語 | Rust |
| 最初の対象言語 | Java |
| 辞書の書き方 | 許可するものだけを書く（許可リスト方式）。禁止する動詞や同義語のリストは持たない |
| ドメインイベント | 辞書には書かない。名詞と振る舞い（の過去分詞）の組み合わせとして検証する |
| アクセサ | 特別扱いしない。DTO などの例外は設定ファイルのルールで表現する |
| 辞書の編集 | エージェントには辞書ファイルを直接編集させず、用語の追加・編集・削除はコマンドを経由させる（M7）。コマンドが書き込む前に検証するので、エージェントが壊れた辞書を作ることがない |
| ルールの置き場所 | コアは具体的な命名や用語に依存しない抽象的な判定だけを実装する。具体的なルールは設定ファイルで定義し、後から変えられるようにする |
| YAML パーサ | `saphyr`。Rust だけで書かれた YAML 1.2 のパーサで、各ノードの位置を取得できる。serde を介さずに自前で変換し、ファイル内のすべての問題を位置付きでまとめて報告する |

## 2. 判定の考え方

コアが実装する判定は次の 1 つだけです。

> 識別子を単語列に分割し、その識別子に適用されるパターンのどれかに一致するか調べる。パターン中の動詞は、結びつく名詞の `behaviors` に含まれていなければならない。

どのパターンにも一致しない識別子は違反になります。禁止リストを持たなくても、次のようなものはすべて違反として検出できます。

- 汎用的な CRUD 動詞（`updateOrder()` の `update` は `Order` の振る舞いにない）
- 辞書にない同義語（`PurchaseService` の `purchase` は辞書にない）
- 振る舞いとして定義されていない動詞から作ったイベント名（`OrderUpdated`）

品詞解析は行いません。どの位置に動詞が来るかはパターンが決めるので、単語の品詞を知る必要はありません。

### 2.1 パターンの部品

| 部品 | 意味 |
|---|---|
| `{noun}` / `{noun:plural}` | 辞書にある名詞（単数形 / 複数形）。`LineItem` のように複数の単語でできた名詞にも一致する。単数形は `{noun:singular}` とも書ける |
| `{verb}` | 結びつく名詞の振る舞いの原形。`{verb:base}` とも書ける |
| `{verb:s}` / `{verb:past}` / `{verb:pp}` / `{verb:ing}` | 同じく三人称単数形 / 過去形 / 過去分詞 / 動名詞 |
| `{<語彙名>}` | 設定ファイルの `vocabularies` で定義した単語のリスト（例: `{role}`） |
| `{any}` | 任意の単語列 |
| `get`、`Event` などの文字列 | その単語そのもの。識別子と同じ規則（2.3）で単語列に分割し、大文字・小文字を区別せずに比較する。`findAll` のように複数の単語を含んでもよい。使える文字は ASCII の英数字と `_` で、`_` は識別子と同様に区切りとして無視される |

`{verb}` が結びつく名詞は、まず同じ識別子の中から探し、見つからなければ外側の型の名詞を使います。たとえば `Order` クラスのメソッド `place()` は、外側の型 `Order` の振る舞いとして検証します。「外側の型」は、そのシンボルを直接囲んでいる最も内側の型を指します。どの型が囲んでいるかは、アダプタが返す親子関係から判断します（6 章）。

### 2.2 違反メッセージ

違反メッセージは、最も近いパターンとの差分から組み立てます。たとえば `updateOrder()` なら次のように返します。

```
`{verb}{noun}` の名詞には `Order` が一致しましたが、`update` は `Order` の振る舞いにありません（定義済み: place, cancel）
```

定義済みの振る舞いを一覧で返すことで、エージェントが候補と `description` を見て自分で直せるようにします。

### 2.3 識別子の分割

識別子は、次の規則で小文字の単語列に分割します。規則は識別子の文字だけで決まり、辞書や設定には左右されません。

| 規則 | 例 |
|---|---|
| 英数字以外の文字（`_`、`$` など）は区切りになる | `ORDER_ID` → `order id` |
| 小文字の直後の大文字から新しい単語が始まる | `placeOrder` → `place order` |
| 大文字が続くとき、小文字の直前にある最後の大文字から新しい単語が始まる | `HTTPOrderClient` → `http order client` |
| ただし、大文字の連続の直後に単語末尾の `s` が 1 文字だけ続く場合は、略語の複数形として 1 語にまとめる。`s` のあとに数字が続いても同じ | `URLs` → `urls`、`IDsByOrder` → `ids by order`、`URLs2Csv` → `urls2 csv` |
| 数字は直前の単語にくっつき、それ自体では単語を区切らない | `base64Encode` → `base64 encode`、`B2BOrder` → `b2b order` |
| 区切りの直後や先頭の数字は、続く文字と同じ単語になる | `3DSecure` → `3d secure`、`2FA` → `2fa` |
| 日本語のように大文字・小文字のない文字は、小文字と同じに扱う | `注文Service` → `注文 service` |

これらの規則は、`IPv4Address` のように大文字と小文字が不規則に混ざった表記を `i pv4 address` と分割します。こうした表記を特別扱いすると規則が辞書に依存してしまうため、例外は設けません。

## 3. 辞書スキーマ（`terms.yaml`）v0

辞書には「どんな用語があり、何ができるか」だけを書きます。語形変化はすべて辞書にあらかじめ展開しておき、リンターは完全一致だけで判定します。

```yaml
# src/main/java/com/example/order/terms.yaml
context: order
terms:
  - name: Order
    kind: entity
    ja: 注文
    description: 顧客が確定させた購入の単位
    forms: { singular: order, plural: orders }
    behaviors:
      - verb: place
        forms: { base: place, s: places, past: placed, pp: placed, ing: placing }
      - verb: cancel
        forms: { base: cancel, s: cancels, past: canceled, pp: canceled, ing: canceling }
```

| フィールド | 必須 | 説明 |
|---|---|---|
| `context` | ○ | 境界づけられたコンテキストの名前 |
| `terms` | ○ | 用語のリスト |
| `terms[].name` | ○ | 用語の正式な表記。ASCII の英数字で、英字から始める（例: `LineItem`） |
| `terms[].kind` | | 用語の種類（`entity`、`value_object` など）。値は自由に決めてよい |
| `terms[].ja` | | 日本語のラベル。日本語で指示を受けたエージェントが、正しい識別子に対応づけるために使う |
| `terms[].description` | | 用語の意味 |
| `terms[].forms` | ○ | 名詞の語形。`singular`（単数形）と `plural`（複数形）の両方が必須 |
| `terms[].behaviors` | | 許可する振る舞いのリスト。省略すると、振る舞いを持たない用語になる |
| `terms[].behaviors[].verb` | ○ | 許可する振る舞い（動詞の原形） |
| `terms[].behaviors[].forms` | ○ | 動詞の語形。`base`（原形）、`s`（三人称単数形）、`past`（過去形）、`pp`（過去分詞）、`ing`（動名詞）のすべてが必須 |

語形と `verb` は単語列で書きます。単語には小文字の英字と数字だけを使い、複数の単語は半角スペース 1 つで区切ります（例: `line item`）。`LineItem` や `line_item` のような書き方はエラーになります。

読み込み時には、次の点も検査します。

- 定義されていないフィールドがないこと（古いスキーマの `forbidden_verbs` などもエラーになる）
- 用語の名前が重複していないこと（大文字・小文字は区別しない）
- 1 つの語形が複数の用語で使われていないこと。ただし、同じ用語の単数形と複数形が同じ（例: `data`）なのはよい
- 同じ用語に同じ振る舞いが重複していないこと
- `forms.base` が `verb` と一致していること
- `forms.singular` が、`name` を 2.3 の規則で分割した単語列と一致していること（例: `name: LineItem` なら `singular: line item`）

### 3.1 辞書の解決規則（M5）

対象のソースファイルと同じディレクトリから親へ遡り、最初に見つかった `terms.yaml` だけを使います。探索の上限は、指定した `ubiqlint.yaml` があるディレクトリです。その上の辞書や、兄弟ディレクトリの辞書は参照しません。

```text
ubiqlint.yaml
terms.yaml                   # ルートの辞書（任意）
src/
  order/
    terms.yaml               # 注文の辞書
    domain/Order.java        # 注文の辞書だけを使用
  billing/
    terms.yaml               # 請求の辞書
    domain/Invoice.java      # 請求の辞書だけを使用
  other/Order.java           # ルートの辞書を使用
```

- **コンテキストの境界**: 辞書を置いた場所でコンテキストを切り替え、親の用語や振る舞いはマージしません。`terms: []` の空の辞書も境界です。別の辞書には同じ名前の用語を異なる意味・振る舞いで定義できます。`context` はラベルであり、同じ値の辞書同士が結合されることもありません
- **ルートの辞書は任意**: パッケージごとの辞書だけでも検査できます。ルールの `include` に一致するソースで探索範囲に辞書がなければ、ファイルのパス付きでエラーにし、他のファイルの検査は続けます。どのルールにも一致しないソースには辞書を要求しませんが、読み込み・構文エラーは従来どおり報告します。構文エラーのあるソースでは辞書の解決・命名検査を行いません。ソースが 0 件なら、従来どおり警告だけを出します
- **壊れた辞書**: 最も近い辞書が不正、読み取り不能、リンク切れなどの場合はエラーにし、親の辞書にはフォールバックしません。同じ辞書の問題は 1 回だけ報告し、他のコンテキストの検査は続けます。ルートに辞書がある場合は、設定ファイルと一緒に先に検証するので、設定と辞書の問題をまとめて報告できます
- **除外との関係**: `.gitignore`・`.ignore`・`exclude` はソースの探索に適用します。辞書は検査対象のソースに必要な定義として直接読み込むため、辞書ファイル自体がこれらに一致していても境界は消えません。ルート以外では、検査対象のソースから参照されない辞書は読みません。辞書自体を検証するには `ubiqlint validate path/to/terms.yaml` を使います
- **パス**: 辞書はシンボリックリンクのリンク先ではなく、探索で見えるソースのパスを基準に選びます。ルールの `include` と同じ基準にするためです
- **明示指定**: `ubiqlint check --dictionary path/to/terms.yaml` は自動解決を無効にし、その辞書だけをすべてのソースに適用します。従来どおり、このパスは実行時のカレントディレクトリからの相対パスとして扱います。自動解決用の辞書は検証しません
- **共有カーネル**: 暗黙の共有や継承は導入しません。共有辞書の明示的な取り込み・合成は将来の拡張とし、M5 では最も近い辞書によるコンテキストの分離に絞ります

解決処理は言語に依存しないコアの `DictionaryResolver` に置き、選ばれた辞書とそのパスを返します。辞書・不存在・読み込み失敗は 1 回の検査中にキャッシュします。編集後に再検査する呼び出し側は、新しい resolver を作ります。

## 4. 設定ファイル（`ubiqlint.yaml`）v0

どの場所の、どの種類の識別子に、どのパターンを適用するかを書きます。

```yaml
# ubiqlint.yaml
exclude: ["src/main/java/**/generated/**"]

vocabularies:
  role: [repository, factory, policy]

rules:
  - id: domain-type
    include: ["src/main/java/**/domain/**"]
    target: type
    patterns:
      - "{noun}"            # Order
      - "{noun}{role}"      # OrderRepository
      - "{noun}{verb:pp}"   # OrderPlaced（ドメインイベント）

  - id: domain-method
    include: ["src/main/java/**/domain/**"]
    target: method
    patterns:
      - "{verb}"            # Order#place()（外側の型の名詞に対して検証する）
      - "{verb}{noun}"      # placeOrder()

  - id: dto
    include: ["src/main/java/**/dto/**"]
    target: method
    patterns:
      - "get{any}"
      - "set{any}"
```

| フィールド | 必須 | 説明 |
|---|---|---|
| `vocabularies` | | パターンから参照する単語列のリスト。名前は小文字の英字・数字・`_` で、英字から始める。`noun`、`verb`、`any` は使えない |
| `rules` | ○ | ルールのリスト |
| `rules[].id` | ○ | ルールの識別子。違反メッセージに含める。小文字の英数字をハイフンでつなぐ（例: `domain-method`）。重複は不可 |
| `rules[].include` | ○ | ルールを適用するパス（glob）のリスト。設定ファイルのあるディレクトリからの相対パスとして照合する。`*` はディレクトリの区切りをまたがず、またぐには `**` を使う |
| `rules[].target` | ○ | 対象とする識別子の種類。`type`（クラス・インターフェース・enum・record など）、`method`、`field`（enum 定数と record コンポーネントを含む）、`parameter`、`variable`（ローカル変数）のいずれか |
| `rules[].patterns` | ○ | 許可するパターンのリスト。どれか 1 つに一致すればよい |
| `exclude` | | 一切検査しないファイルの glob リスト。`include` と同じ glob 作法（`*` はディレクトリの区切りをまたがない）で、設定ファイルのディレクトリからの相対パスと照合する。`.gitignore` とは別に、生成コードなどを明示したい場合に使う。ディレクトリごと除外したいときは `legacy/**` のように `/**` で終わる形で書く（`exclude` はファイルのパスと照合するので、`legacy` だけ書いてもその下のファイルには一致しない） |

`target` には、特定の言語に依存しないよう `class` ではなく `type` を使います。

命名の慣習はこのファイルだけで変えられます。たとえばイベントを `OrderPlacedEvent` の形で命名するチームは、パターンを `{noun}{verb:pp}Event` に書き換えるだけで済みます。テストコードをどう扱うかも `include` で決めます。

許可リスト方式では、どのパターンにも一致しない識別子はすべて違反になります。導入直後に違反が大量に出ないよう、最初はドメイン層のクラス名とメソッド名だけを対象にし、フィールドやローカル変数は必要に応じて設定で広げていく想定です。

## 5. Java 対応の方針

- **構文解析**: `tree-sitter-java` を使い、クラス・インターフェース・enum・record、メソッド、フィールド、引数、ローカル変数、`import` 文を抽出する
- **文法の同梱**: `tree-sitter-java` 0.23.5 は、型パターンと record パターンの要素に修飾子を書いた構文（`case final String s` など）を構文エラーにする。配布元の最新版でも直っていないため、この 2 つの規則に修飾子を許した文法を `vendor/tree-sitter-java` に同梱し、パーサを生成し直して使う。修正の内容と生成し直す手順は、同じディレクトリの README に書く
- **宣言の種類**: Java の宣言は、次のようにシンボルの種類（6 章）に対応づける。設定ファイルの `target` は、コンストラクタ以外の種類と同じ名前を使う

  | Java の宣言 | シンボルの種類 |
  |---|---|
  | クラス、インターフェース、enum、record、アノテーション型 | `type` |
  | 匿名クラス（enum 定数の本体を含む） | `type`（名前なし） |
  | コンストラクタ（record のコンパクトコンストラクタを含む） | `constructor` |
  | メソッド、アノテーション型の要素 | `method` |
  | フィールド、インターフェースの定数、enum 定数、record のコンポーネント | `field` |
  | メソッド・コンストラクタ・ラムダ式の引数、`catch` の例外パラメータ | `parameter` |
  | ローカル変数、拡張 `for` 文や `try` with resources の変数、パターン変数 | `variable` |

  enum 定数と record のコンポーネントは、Java の言語仕様でフィールドとして扱われるので `field` にする。コンストラクタの名前は型の名前で決まるので検査しないが、引数やローカル変数の親として抽出する。無名変数（`_`）とレシーバパラメータ（`Order this`）は抽出しない
- **字句変換**: Java のコンパイラと同じく、解析の前に Unicode エスケープ（`\u004f` など）を文字に置き換え、単独の CR を改行として扱う。`tree-sitter-java` はどちらも行わないため。名前は置き換えた後の文字列で検査し、位置は書かれたままのソースを指す（`class \u004frder` は `Order` という型として検査し、`\u004frder` の位置を報告する）。どのバックスラッシュがエスケープを始めるかは javac に合わせる。形の崩れたエスケープ（`\u00G1` など）は、Java と同じくコメントの中でもエラーとして報告する
- **構文エラー**: 構文エラーのあるファイルは検査せず、構文エラーを位置付きで報告する。パーサが推測で補った構文木を検査すると、誤った違反が出るおそれがあるため
- **辞書の置き場所**: Java ではパッケージとディレクトリが対応しているので、`src/main/java/com/example/order/terms.yaml` のようにパッケージのディレクトリに置く
- **外部ライブラリとの境界**: Java には別名インポートがない。そのため、ドメイン層ではドメイン用語と同じ名前の外部型（例: `com.stripe.model.Customer`）の `import` を禁止し、使う場合は完全修飾名で書かせる
- **ワイルドカードインポート**: `import com.stripe.model.*;` はクラスパスを見ないとどの型が入ってくるか分からないので、ドメイン層では外部パッケージのワイルドカードインポートを禁止する

## 6. アーキテクチャ

```
crates/
  ubiqlint-core   辞書と設定の読み込み・解決、識別子の分割、パターン照合、診断（言語に依存しない）
  ubiqlint-java   tree-sitter-java で識別子とインポートを抽出するアダプタ
  ubiqlint-cli    `ubiqlint check` などのコマンド
  （後で追加）ubiqlint-mcp / ubiqlint-lsp
```

- コアには `LanguageAdapter` トレイトを定義する。アダプタはシンボルの列を返すだけにし、コアは個々のプログラミング言語について何も知らないようにする。各シンボルは次の情報を持つ
  - ID: ファイル内でシンボルを一意に識別する
  - 名前: 匿名クラスのように名前のない宣言では空
  - 種類: `type`、`constructor`、`method`、`field`、`parameter`、`variable` のいずれか
  - 位置: 識別子の位置（違反の報告に使う）と、宣言全体の範囲。行と列はどちらも 1 から数え、列は文字単位で数える（タブや日本語の文字も 1 文字）
  - 親の ID: そのシンボルを直接囲んでいる宣言の ID。トップレベルの宣言では空
- シンボルは親より後にしか追加できないようにする。親は必ず子より前に並ぶので、親をたどる処理は必ず終わる
- 構文エラーのあるファイルについては、アダプタはシンボルの代わりに構文エラーを返す
- コアは親の ID をたどって外側の型を特定する。1 つのファイルに複数の型がある場合や型が入れ子になっている場合でも、コアが構文を解釈したり、位置から包含関係を推測したりする必要がないようにするため
- コアでは、`pattern` がパターンの構文、`matching` が単語列の照合、`check` がシンボルへのルール適用と診断を担当する。照合エンジンはシンボルや診断文に依存しない
- 利用者向けのインターフェースは、CLI（CI 向け）、LSP（エディタ向け）、MCP サーバ（エージェント向け）の 3 つを想定する
- MCP サーバの中心機能は「このファイルに適用される辞書を返す」と「コード片を検査し、違反を定義済みの候補付きで返す」の 2 つ
- Claude Code の hooks でファイル編集のたびにリンターを走らせ、エージェントが違反をその場で受け取って直すループを作る

## 7. マイルストーン

| # | 内容 | ゴール |
|---|---|---|
| M0 | Cargo ワークスペースのひな形、CI（fmt / clippy / test）、`.gitignore` を Rust 用に置き換える | `cargo test` が通る |

## 8. 未決事項

- **`{verb}` と名詞の結びつけ**: 1 つの識別子に名詞が複数含まれる場合の規則。また、最も内側の型から名詞が得られない場合（匿名クラスや、名前に名詞を含まない入れ子の型など）に、さらに外側の型までたどるかどうか
- **enum 定数の対象**: enum 定数（`PLACED` など）は `field` として扱うが、通常のフィールドとは命名の慣習が違う。`target` を分ける必要があるかどうか
- **共有カーネル**: M5 では最も近い辞書だけを使う（3.1）。共有辞書を明示的に取り込み・合成する場合のスキーマと、重複・衝突の扱いは将来の拡張として未決
- **外部ライブラリ境界ルールの設定表現**: 6 章のルールを設定ファイルでどう書くか
- **同綴異義語**: `orderBy` や `sortOrder` のように、ドメイン用語と同じ綴りの一般語を含む識別子の扱い
- **米英の綴り**: `canceled` / `cancelled` のどちらを使うか、両方を許すか
- **出力形式**: テキスト、JSON、SARIF のどれに対応するか
- **既存コードへの導入**: 既存の違反をまとめて抑制するベースラインの仕組み
- **辞書を編集するコマンド**: コマンドの体系（サブコマンドの名前や引数）、語形をどう指定させるか、書き換えたときに YAML のコメントや書式を保つかどうか
