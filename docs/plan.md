# ubiqlint 実装計画

この文書は、ubiqlint の実装方針とマイルストーンを記録するものです。背景・目的・設計原則は[構想文書](concept.md)にまとめており、ここではそれを実装に落とすにあたって決めたことを書きます。

ubiqlint は、ユビキタス言語を「人間が守るよう努める約束事」から「コーディングエージェントとコードベースを機械的に縛るルール」に変えるためのリンターです。機械可読な辞書を用意し、コード中の識別子が辞書に沿っているかを静的に検査します。

## 1. 決定事項

| 項目 | 決定内容 |
|---|---|
| 実装言語 | Rust |
| 最初の対象言語 | Java |
| 辞書の書き方 | 許可するものだけを書く（許可リスト方式）。禁止する動詞や同義語のリストは持たない |
| ドメインイベント | 辞書には書かない。名詞と振る舞い（の過去分詞）の組み合わせとして検証する |
| アクセサ | 特別扱いしない。DTO などの例外は設定ファイルのルールで表現する |
| 辞書の編集 | エージェントには辞書ファイルを直接編集させず、用語と振る舞いの追加・編集・削除は `ubiqlint term` / `ubiqlint behavior` コマンドを経由させる（M7、3.2 節）。コマンドが書き込む前に検証するので、エージェントが壊れた辞書を作ることがない。変更しない部分のコメントや書式はそのまま残す |
| ルールの置き場所 | コアは具体的な命名や用語に依存しない抽象的な判定だけを実装する。具体的なルールは設定ファイルで定義し、後から変えられるようにする |
| YAML パーサ | `saphyr`。Rust だけで書かれた YAML 1.2 のパーサで、各ノードの位置を取得できる。serde を介さずに自前で変換し、ファイル内のすべての問題を位置付きでまとめて報告する |
| エージェントとの連携 | MCP サーバ（M8、6.2 節）と LSP サーバ（M9、6.3 節）で提供する。特定のエージェントの hooks には対応しない（6.4 節） |
| 辞書の変更の判断 | 人の承認は挟まない。実装からレビューまで AI エージェントが担う運用を想定し、違反を消すためだけの辞書の変更は、レビューするエージェントが止める（6.2 節） |

## 2. 判定の考え方

コアが実装する判定は次の 1 つだけです。

> 識別子を単語列に分割し、その識別子に適用されるパターンのどれかに一致するか調べる。パターン中の動詞は、結びつく名詞の `behaviors` に含まれていなければならない。

どのパターンにも一致しない識別子は違反になります。禁止リストを持たなくても、次のようなものはすべて違反として検出できます。

- 汎用的な CRUD 動詞（`updateOrder()` の `update` は `Order` の振る舞いにない）
- 辞書にない同義語（`PurchaseService` の `purchase` は辞書にない）
- 振る舞いとして定義されていない動詞から作ったイベント名（`OrderUpdated`）

品詞解析は行いません。どの位置に動詞が来るかはパターンが決めるので、単語の品詞を知る必要はありません。

### 2.1 パターンの部品

| 部品 | 意味 |
|---|---|
| `{noun}` / `{noun:plural}` | 辞書にある名詞（単数形 / 複数形）。`LineItem` のように複数の単語でできた名詞にも一致する。単数形は `{noun:singular}` とも書ける |
| `{verb}` | 結びつく名詞の振る舞いの原形。`{verb:base}` とも書ける |
| `{verb:s}` / `{verb:past}` / `{verb:pp}` / `{verb:ing}` | 同じく三人称単数形 / 過去形 / 過去分詞 / 動名詞 |
| `{<語彙名>}` | 設定ファイルの `vocabularies` で定義した単語のリスト（例: `{role}`） |
| `{any}` | 任意の単語列 |
| `get`、`Event` などの文字列 | その単語そのもの。識別子と同じ規則（2.3）で単語列に分割し、大文字・小文字を区別せずに比較する。`findAll` のように複数の単語を含んでもよい。使える文字は ASCII の英数字と `_` で、`_` は識別子と同様に区切りとして無視される |

`{verb}` が結びつく名詞は、まず同じ識別子の中から探し、見つからなければ外側の型の名詞を使います。たとえば `Order` クラスのメソッド `place()` は、外側の型 `Order` の振る舞いとして検証します。「外側の型」は、そのシンボルを直接囲んでいる最も内側の型を指します。どの型が囲んでいるかは、アダプタが返す親子関係から判断します（6 章）。

### 2.2 違反メッセージ

違反メッセージは、最も近いパターンとの差分から組み立てます。たとえば `updateOrder()` なら次のように返します。

```
`{verb}{noun}` の名詞には `Order` が一致しましたが、`update` は `Order` の振る舞いにありません（定義済み: place, cancel）
```

定義済みの振る舞いを一覧で返すことで、エージェントが候補と `description` を見て自分で直せるようにします。

### 2.3 識別子の分割

識別子は、次の規則で小文字の単語列に分割します。規則は識別子の文字だけで決まり、辞書や設定には左右されません。

| 規則 | 例 |
|---|---|
| 英数字以外の文字（`_`、`$` など）は区切りになる | `ORDER_ID` → `order id` |
| 小文字の直後の大文字から新しい単語が始まる | `placeOrder` → `place order` |
| 大文字が続くとき、小文字の直前にある最後の大文字から新しい単語が始まる | `HTTPOrderClient` → `http order client` |
| ただし、大文字の連続の直後に単語末尾の `s` が 1 文字だけ続く場合は、略語の複数形として 1 語にまとめる。`s` のあとに数字が続いても同じ | `URLs` → `urls`、`IDsByOrder` → `ids by order`、`URLs2Csv` → `urls2 csv` |
| 数字は直前の単語にくっつき、それ自体では単語を区切らない | `base64Encode` → `base64 encode`、`B2BOrder` → `b2b order` |
| 区切りの直後や先頭の数字は、続く文字と同じ単語になる | `3DSecure` → `3d secure`、`2FA` → `2fa` |
| 日本語のように大文字・小文字のない文字は、小文字と同じに扱う | `注文Service` → `注文 service` |

これらの規則は、`IPv4Address` のように大文字と小文字が不規則に混ざった表記を `i pv4 address` と分割します。こうした表記を特別扱いすると規則が辞書に依存してしまうため、例外は設けません。

## 3. 辞書スキーマ（`terms.yaml`）v0

辞書には「どんな用語があり、何ができるか」だけを書きます。語形変化はすべて辞書にあらかじめ展開しておき、リンターは完全一致だけで判定します。

```yaml
# src/main/java/com/example/order/terms.yaml
context: order
terms:
  - name: Order
    kind: entity
    ja: 注文
    description: 顧客が確定させた購入の単位
    forms: { singular: order, plural: orders }
    behaviors:
      - verb: place
        forms: { base: place, s: places, past: placed, pp: placed, ing: placing }
      - verb: cancel
        forms: { base: cancel, s: cancels, past: canceled, pp: canceled, ing: canceling }
```

| フィールド | 必須 | 説明 |
|---|---|---|
| `context` | ○ | 境界づけられたコンテキストの名前 |
| `terms` | ○ | 用語のリスト |
| `terms[].name` | ○ | 用語の正式な表記。ASCII の英数字で、英字から始める（例: `LineItem`） |
| `terms[].kind` | | 用語の種類（`entity`、`value_object` など）。値は自由に決めてよい |
| `terms[].ja` | | 日本語のラベル。日本語で指示を受けたエージェントが、正しい識別子に対応づけるために使う |
| `terms[].description` | | 用語の意味 |
| `terms[].forms` | ○ | 名詞の語形。`singular`（単数形）と `plural`（複数形）の両方が必須 |
| `terms[].behaviors` | | 許可する振る舞いのリスト。省略すると、振る舞いを持たない用語になる |
| `terms[].behaviors[].verb` | ○ | 許可する振る舞い（動詞の原形） |
| `terms[].behaviors[].forms` | ○ | 動詞の語形。`base`（原形）、`s`（三人称単数形）、`past`（過去形）、`pp`（過去分詞）、`ing`（動名詞）のすべてが必須 |

語形と `verb` は単語列で書きます。単語には小文字の英字と数字だけを使い、複数の単語は半角スペース 1 つで区切ります（例: `line item`）。`LineItem` や `line_item` のような書き方はエラーになります。

読み込み時には、次の点も検査します。

- 定義されていないフィールドがないこと（古いスキーマの `forbidden_verbs` などもエラーになる）
- 用語の名前が重複していないこと（大文字・小文字は区別しない）
- 1 つの語形が複数の用語で使われていないこと。ただし、同じ用語の単数形と複数形が同じ（例: `data`）なのはよい
- 同じ用語に同じ振る舞いが重複していないこと
- `forms.base` が `verb` と一致していること
- `forms.singular` が、`name` を 2.3 の規則で分割した単語列と一致していること（例: `name: LineItem` なら `singular: line item`）

### 3.1 辞書の解決規則（M5）

対象のソースファイルと同じディレクトリから親へ遡り、最初に見つかった `terms.yaml` だけを使います。探索の上限は、指定した `ubiqlint.yaml` があるディレクトリです。その上の辞書や、兄弟ディレクトリの辞書は参照しません。

```text
ubiqlint.yaml
terms.yaml                   # ルートの辞書（任意）
src/
  order/
    terms.yaml               # 注文の辞書
    domain/Order.java        # 注文の辞書だけを使用
  billing/
    terms.yaml               # 請求の辞書
    domain/Invoice.java      # 請求の辞書だけを使用
  other/Order.java           # ルートの辞書を使用
```

- **コンテキストの境界**: 辞書を置いた場所でコンテキストを切り替え、親の用語や振る舞いはマージしません。`terms: []` の空の辞書も境界です。別の辞書には同じ名前の用語を異なる意味・振る舞いで定義できます。`context` はラベルであり、同じ値の辞書同士が結合されることもありません
- **ルートの辞書は任意**: パッケージごとの辞書だけでも検査できます。ルールの `include` に一致するソースで探索範囲に辞書がなければ、探索を始めたソースのディレクトリごとに 1 回だけ、そのディレクトリのパス付きでエラーを報告します。他のファイルの検査は続けます。どのルールにも一致しないソースには辞書を要求しませんが、読み込み・構文エラーは従来どおり報告します。構文エラーのあるソースでは命名検査と辞書エラーの報告を行いません。ソースが 0 件なら、従来どおり警告だけを出します
- **壊れた辞書**: 最も近い辞書が不正、読み取り不能、リンク切れなどの場合はエラーにし、親の辞書にはフォールバックしません。同じ辞書の問題は 1 回だけ報告し、他のコンテキストの検査は続けます。ルートに辞書がある場合は、設定ファイルと一緒に先に検証するので、設定と辞書の問題をまとめて報告できます
- **除外との関係**: `.gitignore`・`.ignore`・`exclude` はソースの探索に適用します。辞書は検査対象のソースに必要な定義として直接読み込むため、辞書ファイル自体がこれらに一致していても境界は消えません。ルート以外では、ルールの `include` に一致するソースから参照される辞書だけ先読みします。ソース自体の読み込み・構文エラーがある場合、そのソースに対応する辞書の問題は報告しません。辞書自体を検証するには `ubiqlint validate path/to/terms.yaml` を使います
- **パス**: 辞書はシンボリックリンクのリンク先ではなく、探索で見えるソースのパスを基準に選びます。ルールの `include` と同じ基準にするためです
- **明示指定**: `ubiqlint check --dictionary path/to/terms.yaml` は自動解決を無効にし、その辞書だけをすべてのソースに適用します。従来どおり、このパスは実行時のカレントディレクトリからの相対パスとして扱います。自動解決用の辞書は検証しません
- **診断の辞書パス**: 用語追加のヒントと「外側の型が辞書にない」という診断には、実際に適用した辞書のパスを含めます。自動解決では選ばれた `terms.yaml`、明示指定では `--dictionary` のパスを示します
- **共有カーネル**: 暗黙の共有や継承は導入しません。共有辞書の明示的な取り込み・合成は将来の拡張とし、M5 では最も近い辞書によるコンテキストの分離に絞ります

解決処理は言語に依存しないコアの `DictionaryResolver` に置き、選ばれた辞書とそのパスを返します。辞書・不存在・読み込み失敗は 1 回の検査中にキャッシュします。検査する側（M8 からは `ubiqlint-project` の `CheckRun`、6.1 節）は対象ディレクトリの解決を済ませてから、`loaded_dictionary` で辞書とそのパスを共有参照し、辞書のパスごとに `Checker` と照合用の索引を 1 度だけ作って使い回します。編集後に再検査する呼び出し側は、新しい resolver を作ります。

### 3.2 辞書を編集するコマンド（M7）

用語と振る舞いは、次のコマンドで追加・編集・削除します。エージェントには辞書ファイルを直接書き換えさせず、これらのコマンドを使わせます。

| コマンド | 内容 |
|---|---|
| `ubiqlint term add <NAME> --plural <WORDS> [--kind <TEXT>] [--ja <TEXT>] [--description <TEXT>]` | 振る舞いのない用語を、最後の用語の後に追加する |
| `ubiqlint term edit <NAME> [--name <NAME>] [--plural <WORDS>] [--kind <TEXT> \| --unset-kind] [--ja <TEXT> \| --unset-ja] [--description <TEXT> \| --unset-description]` | 用語のフィールドを変更する。少なくとも 1 つの変更が必要 |
| `ubiqlint term remove <NAME>` | 用語を振る舞いごと削除する |
| `ubiqlint behavior add <TERM> <VERB> --s <WORDS> --past <WORDS> --pp <WORDS> --ing <WORDS>` | 用語の最後の振る舞いの後に振る舞いを追加する |
| `ubiqlint behavior edit <TERM> <VERB> [--verb <WORDS>] [--s <WORDS>] [--past <WORDS>] [--pp <WORDS>] [--ing <WORDS>]` | 振る舞いを変更する。少なくとも 1 つの変更が必要 |
| `ubiqlint behavior remove <TERM> <VERB>` | 振る舞いを削除する |

```sh
ubiqlint term add Shipment --plural shipments --kind entity --ja 出荷 \
  --dictionary src/main/java/com/example/order/terms.yaml
ubiqlint behavior add Shipment ship --s ships --past shipped --pp shipped --ing shipping \
  --dictionary src/main/java/com/example/order/terms.yaml
```

- **編集する辞書**: `--dictionary` で指定します。省略すると、カレントディレクトリの `terms.yaml` を編集します。`check --dictionary` と同じく、カレントディレクトリからの相対パスとして扱います。どの辞書に書けばよいかは、`check` の違反メッセージにある辞書のパス（3.1 節）で分かります。辞書を置く場所はコンテキストの境界を決めるため、辞書ファイルの新規作成はコマンドで行いません
- **語形の指定**: コマンドは語形を推測しません。単数形は `name` を 2.3 節の規則で分割した単語列、`forms.base` は `verb` と決まっているので自動で書きます。それ以外の語形（複数形、三人称単数形、過去形、過去分詞、動名詞）は、すべて引数で指定します。不規則変化や `canceled` / `cancelled` のような綴りの違いを、コマンドが勝手に決めないようにするためです
- **名前の変更**: `term edit --name` は単数形も書き換えます。単数形が変わる場合（`LineItem` → `OrderLine`）は `--plural` も必要です。単語列が変わらない場合（`Sku` → `SKU`）は不要です。`behavior edit --verb` は `forms.base` も書き換えるので、残りの 4 つの語形もすべて指定します
- **対象の指定**: 用語は `name` と完全に一致する名前（大文字・小文字を区別する）で、振る舞いは `verb` の単語列で指定します。見つからなければ、定義済みの用語や振る舞いの一覧をエラーに含めます
- **検証**: 引数の書式（用語名、単語列、空でない文字列）の誤りは、使い方のエラーとして終了コード 2 で報告します。辞書が不正な場合は、`validate` と同じ診断を出して編集しません。用語名の重複（大文字・小文字は区別しない）、他の用語が使っている語形、同じ用語での振る舞いの重複など、辞書と矛盾する編集は、すべての問題をまとめて報告して終了コード 1 で失敗します。いずれの場合もファイルは変更しません
- **書き込む前の確認**: 書き換えた結果を辞書として読み直し、意図した内容と完全に一致する場合だけ書き込みます。値がすでに同じなら書き込まず、変更がない旨を出力して終了コード 0 で終わります。成功したときは ``terms.yaml: added term `Shipment` `` のように、辞書のパスと行った変更を出力します
- **書式の保持**: 変更する行だけを書き換え、それ以外のコメント・空行・書式・改行コードはそのまま残します
  - 用語や振る舞いは最後の要素の後に追加し、インデントは隣の要素に合わせます。振る舞いを初めて追加する用語では、`terms` の並べ方に合わせます。`forms` は、ファイルの最初の `forms` と同じ書き方（`{ ... }` か、1 行に 1 フィールドか）にします
  - 足りないフィールドは、スキーマの順序（`name`、`kind`、`ja`、`description`、`forms`、`behaviors`）に従って挿入します
  - 値は、そのまま書くと別の値として読まれるもの（`null` や、`: `・` #` を含む文字列、改行を含む文字列など）だけダブルクォートで囲みます
  - 削除では、その要素やフィールドの行と、その範囲にあるコメントを消します。直前のコメントは、まとまりの見出しかもしれないので残します。最後の用語を削除すると `terms: []` になり、最後の振る舞いを削除すると `behaviors` フィールドごと消えます
  - `terms: [ ... ]` のようなフロースタイルへの要素の追加・削除など、行単位で書き換えられない箇所はエラーにし、書式を作り直すことはしません。空の `[]` への追加と、フロースタイル内の値の置き換えはできます
- **ファイルの置き換え**: 同じディレクトリの一時ファイルに書いてから置き換えるので、途中で失敗しても元の辞書は壊れません。一時ファイルは既存のファイルがない場合だけ作成し、同じ名前のファイルやシンボリックリンクがあれば、それには書き込まず消しもせずにエラーにします。シンボリックリンクはリンク先のファイルを書き換え、パーミッションは元のファイルに合わせます

編集処理はコアの `edit` モジュールに置きます。`edit::apply` は辞書のテキストと編集内容（`Edit`）を受け取り、検証してから新しいテキストを返します。ファイルの読み書きは呼び出し側が行うので、M8 の MCP サーバからも同じ処理を使えます。

## 4. 設定ファイル（`ubiqlint.yaml`）v0

どの場所の、どの種類の識別子に、どのパターンを適用するかを書きます。

```yaml
# ubiqlint.yaml
exclude: ["src/main/java/**/generated/**"]

vocabularies:
  role: [repository, factory, policy]

rules:
  - id: domain-type
    include: ["src/main/java/**/domain/**"]
    target: type
    patterns:
      - "{noun}"            # Order
      - "{noun}{role}"      # OrderRepository
      - "{noun}{verb:pp}"   # OrderPlaced（ドメインイベント）

  - id: domain-method
    include: ["src/main/java/**/domain/**"]
    target: method
    patterns:
      - "{verb}"            # Order#place()（外側の型の名詞に対して検証する）
      - "{verb}{noun}"      # placeOrder()

  - id: dto
    include: ["src/main/java/**/dto/**"]
    target: method
    patterns:
      - "get{any}"
      - "set{any}"
```

| フィールド | 必須 | 説明 |
|---|---|---|
| `vocabularies` | | パターンから参照する単語列のリスト。名前は小文字の英字・数字・`_` で、英字から始める。`noun`、`verb`、`any` は使えない |
| `rules` | | 命名ルールのリスト。`rules` と `import_rules` の少なくとも一方を指定する。明示的な空リストも許可する |
| `rules[].id` | ○ | ルールの識別子。違反メッセージに含める。小文字の英数字をハイフンでつなぐ（例: `domain-method`）。重複は不可 |
| `rules[].include` | ○ | ルールを適用するパス（glob）のリスト。設定ファイルのあるディレクトリからの相対パスとして照合する。`*` はディレクトリの区切りをまたがず、またぐには `**` を使う |
| `rules[].target` | ○ | 対象とする識別子の種類。`type`（クラス・インターフェース・enum・record など）、`method`、`field`（enum 定数と record コンポーネントを含む）、`parameter`、`variable`（ローカル変数）のいずれか |
| `rules[].patterns` | ○ | 許可するパターンのリスト。どれか 1 つに一致すればよい |
| `exclude` | | 一切検査しないファイルの glob リスト。`include` と同じ glob 作法（`*` はディレクトリの区切りをまたがない）で、設定ファイルのディレクトリからの相対パスと照合する。`.gitignore` とは別に、生成コードなどを明示したい場合に使う。ディレクトリごと除外したいときは `legacy/**` のように `/**` で終わる形で書く（`exclude` はファイルのパスと照合するので、`legacy` だけ書いてもその下のファイルには一致しない） |

`target` には、特定の言語に依存しないよう `class` ではなく `type` を使います。

命名の慣習はこのファイルだけで変えられます。たとえばイベントを `OrderPlacedEvent` の形で命名するチームは、パターンを `{noun}{verb:pp}Event` に書き換えるだけで済みます。テストコードをどう扱うかも `include` で決めます。

許可リスト方式では、どのパターンにも一致しない識別子はすべて違反になります。導入直後に違反が大量に出ないよう、最初はドメイン層のクラス名とメソッド名だけを対象にし、フィールドやローカル変数は必要に応じて設定で広げていく想定です。

### 4.1 インポート境界ルール

インポート境界は、命名パターンとは別の `import_rules` に書きます。省略した場合はインポートを検査せず、従来の設定をそのまま使えます。

インポート境界だけを検査する場合は `rules` を省略できます。`rules` と `import_rules` が両方ともない設定はエラーです。

```yaml
import_rules:
  - id: domain-imports
    include: ["src/main/java/**/domain/**"]
    internal_namespaces: [com.example.order, com.example.shared]
```

| フィールド | 必須 | 説明 |
|---|---|---|
| `import_rules` | | インポート境界ルールのリスト。`rules` と `import_rules` の少なくとも一方を指定する。空リストでもよい |
| `import_rules[].id` | ○ | 命名ルールと同じ形式の識別子。`rules` と `import_rules` を通じて一意にする |
| `import_rules[].include` | ○ | 検査するファイルの glob リスト。`rules[].include` と同じ作法で、設定ファイルのあるディレクトリからの相対パスと照合する |
| `import_rules[].internal_namespaces` | ○ | 内部として扱う名前空間の接頭辞。`.` で区切った名前を書き、ワイルドカードは使わない。各部分は文字・`_`・`$` で始まり、以降は数字も使える。空リストならすべてのインポート元を外部とする |

`com.example.order` はその名前空間と配下（`com.example.order.model` など）を含みますが、`com.example.ordering` は含みません。大文字・小文字も区別します。Java ではパッケージ名を指定し、ソースファイル自身の `package` 宣言やファイルの配置から内部パッケージを推測しません。共有カーネルなどを内部として扱う場合は、そのパッケージも明示します。

各ルールは、外部から導入される名前が辞書の `terms[].name` と完全一致するインポートと、外部のワイルドカードインポートを禁止します。辞書は 3.1 節の解決規則で選び、命名ルールがなくインポートルールだけのファイルにも最も近い辞書を適用します。親・兄弟の辞書はマージせず、`--dictionary` が指定された場合はその辞書だけを使います。`Order` に対して `Orders` や `OrderDto` は衝突とせず、命名パターンのような単語への分割も行いません。同じファイルに複数のインポートルールが当たる場合は、すべてを満たす必要があります。`exclude` はインポート検査にも適用されます。

構想 2.4 節の `Item` と `MenuItem` のように、用語を一部に含む外部型の判定は M6 の範囲に含めません。これをインポート境界で扱うかどうかは、8 章の未決事項として残します。

違反は `import` 文の先頭の位置とルール ID を付けて報告し、用語との衝突には適用した辞書のパスも含めます。完全修飾名での利用などの修正方法を示し、命名違反と合わせてファイル内の位置順で出力します。

## 5. Java 対応の方針

- **構文解析**: `tree-sitter-java` を使い、クラス・インターフェース・enum・record、メソッド、フィールド、引数、ローカル変数、`import` 文を抽出する
- **文法の同梱**: `tree-sitter-java` 0.23.5 は、型パターンと record パターンの要素に修飾子を書いた構文（`case final String s` など）を構文エラーにする。配布元の最新版でも直っていないため、この 2 つの規則に修飾子を許した文法を `vendor/tree-sitter-java` に同梱し、パーサを生成し直して使う。修正の内容と生成し直す手順は、同じディレクトリの README に書く
- **宣言の種類**: Java の宣言は、次のようにシンボルの種類（6 章）に対応づける。設定ファイルの `target` は、コンストラクタ以外の種類と同じ名前を使う

  | Java の宣言 | シンボルの種類 |
  |---|---|
  | クラス、インターフェース、enum、record、アノテーション型 | `type` |
  | 匿名クラス（enum 定数の本体を含む） | `type`（名前なし） |
  | コンストラクタ（record のコンパクトコンストラクタを含む） | `constructor` |
  | メソッド、アノテーション型の要素 | `method` |
  | フィールド、インターフェースの定数、enum 定数、record のコンポーネント | `field` |
  | メソッド・コンストラクタ・ラムダ式の引数、`catch` の例外パラメータ | `parameter` |
  | ローカル変数、拡張 `for` 文や `try` with resources の変数、パターン変数 | `variable` |

  enum 定数と record のコンポーネントは、Java の言語仕様でフィールドとして扱われるので `field` にする。コンストラクタの名前は型の名前で決まるので検査しないが、引数やローカル変数の親として抽出する。無名変数（`_`）とレシーバパラメータ（`Order this`）は抽出しない
- **字句変換**: Java のコンパイラと同じく、解析の前に Unicode エスケープ（`\u004f` など）を文字に置き換え、単独の CR を改行として扱う。`tree-sitter-java` はどちらも行わないため。名前は置き換えた後の文字列で検査し、位置は書かれたままのソースを指す（`class \u004frder` は `Order` という型として検査し、`\u004frder` の位置を報告する）。どのバックスラッシュがエスケープを始めるかは javac に合わせる。形の崩れたエスケープ（`\u00G1` など）は、Java と同じくコメントの中でもエラーとして報告する
- **構文エラー**: 構文エラーのあるファイルは検査せず、構文エラーを位置付きで報告する。パーサが推測で補った構文木を検査すると、誤った違反が出るおそれがあるため
- **辞書の置き場所**: Java ではパッケージとディレクトリが対応しているので、`src/main/java/com/example/order/terms.yaml` のようにパッケージのディレクトリに置く
- **外部ライブラリとの境界**: Java には別名インポートがない。そのため、ドメイン層ではドメイン用語と同じ名前の外部型（例: `com.stripe.model.Customer`）の `import` を禁止し、使う場合は完全修飾名で書かせる
- **ワイルドカードインポート**: `import com.stripe.model.*;` はクラスパスを見ないとどの型が入ってくるか分からないので、ドメイン層では外部パッケージのワイルドカードインポートを禁止する
- **モジュールインポート（Java 25）**: `import module java.base;`（JEP 511）は同梱の `tree-sitter-java` 0.23.5 では未対応で、構文エラーになる。そのファイルは命名検査・インポート境界検査ともに行わない。文法を更新して対応する際は、外部モジュールのインポートも外部ワイルドカードと同じく禁止する。モジュール名はパッケージ名とは異なるため、内部モジュールの指定方法とインポートの表現も同時に設計する
- **static インポート**: `import static com.vendor.Container.Order;` は入れ子の型も導入できる。クラスパスを見ずに型・フィールド・メソッドを区別することはできないため、外部から導入する最後の名前が辞書の用語と一致する場合は、いずれでも違反にする。`import static com.vendor.Order.create;` が導入するのは `create` なので、辞書に `Order` があってもそれだけでは違反にならない。外部の `import static com.vendor.Order.*;` もワイルドカードとして禁止する
- **検査の範囲**: 明示的な `import` 文だけを検査する。完全修飾名での利用は許可し、同じパッケージや `java.lang` からの暗黙の型参照、参照先の実在や可視性の確認は行わない

## 6. アーキテクチャ

```
crates/
  ubiqlint-core      辞書と設定の読み込み・解決、識別子の分割、パターン照合、診断（言語に依存しない）
  ubiqlint-java      tree-sitter-java で識別子とインポートを抽出するアダプタ
  ubiqlint-project   ファイル探索と 1 ファイルの検査、辞書の書き込み（CLI・MCP・LSP で共通。M8、6.1 節）
  ubiqlint-mcp       MCP サーバ（M8、6.2 節）
  ubiqlint-lsp       LSP サーバ（M9、6.3 節）
  ubiqlint-cli       `ubiqlint check` などのコマンド。`ubiqlint mcp` と `ubiqlint lsp` もここから起動する
```

- コアには `LanguageAdapter` トレイトを定義する。アダプタは宣言とインポートを別々に持つ `SourceFile` を返し、コアは個々のプログラミング言語について何も知らないようにする。各シンボルは次の情報を持つ
  - ID: ファイル内でシンボルを一意に識別する
  - 名前: 匿名クラスのように名前のない宣言では空
  - 種類: `type`、`constructor`、`method`、`field`、`parameter`、`variable` のいずれか
  - 位置: 識別子の位置（違反の報告に使う）と、宣言全体の範囲。行と列はどちらも 1 から数え、列は文字単位で数える（タブや日本語の文字も 1 文字）
  - 親の ID: そのシンボルを直接囲んでいる宣言の ID。トップレベルの宣言では空
- シンボルは親より後にしか追加できないようにする。親は必ず子より前に並ぶので、親をたどる処理は必ず終わる
- インポートは名前空間の要素列、ワイルドカードかどうか、文全体の範囲を持つ。名前付きインポートは最後の要素が導入する名前、それより前がインポート元の名前空間になる。ワイルドカードでは要素列全体がインポート元になる。アダプタがコメントや空白を取り除き、Unicode エスケープなどを変換して要素列を作る。インポートはシンボルの親子関係には含めない
- 構文エラーのあるファイルについては、アダプタは `SourceFile` の代わりに構文エラーを返す
- コアは親の ID をたどって外側の型を特定する。1 つのファイルに複数の型がある場合や型が入れ子になっている場合でも、コアが構文を解釈したり、位置から包含関係を推測したりする必要がないようにするため
- コアでは、`pattern` がパターンの構文、`matching` が単語列の照合、`check` がシンボルとインポートへのルール適用と診断を担当する。`Checker::check_file` は両方を検査し、`Checker::check` はシンボルだけを検査する。照合エンジンはシンボルや診断文に依存しない
- 辞書の編集はコアの `edit` が担当する。編集内容の検証と、コメントや書式を保った YAML の書き換えを行い、ファイルの読み書きは CLI などの呼び出し側に任せる（3.2 節）
- 利用者向けのインターフェースは、CLI（CI 向け）、MCP サーバ（エージェント向け）、LSP サーバ（エディタとエージェント向け）の 3 つ。MCP はエージェントが必要なときに呼ぶもの、LSP は編集のたびに診断を届けるもので、役割が違う
- 3 つとも同じ判定をするよう、検査の流れは `ubiqlint-project` にまとめ、各インターフェースは入出力の変換だけを受け持つ。配布するバイナリは `ubiqlint` の 1 つで、CI で使うリンターとサーバのバージョンが必ずそろう

### 6.1 共通層（M8）

M7 までは、設定の読み込みからファイル探索、辞書の解決、報告までを CLI の `check` が行っていました。MCP サーバと LSP サーバからも同じ判定を呼べるよう、この流れを `ubiqlint-project` に移します。アダプタの一覧とファイル探索（`ignore`）は特定の言語やライブラリに依存するので、コアには入れません。

- **移すもの**: 設定の読み込み、パスの正規化、ファイル探索（`.gitignore`・`.ignore`・`exclude`）、アダプタの選択、1 ファイルの検査、辞書の書き込み（一時ファイルを経由した置き換え。3.2 節）
- **テキストを検査する**: 1 ファイルの検査は、ディスク上のファイルではなく、渡されたテキストに対して行います。MCP の `check_code` や LSP の未保存のバッファも同じ処理で検査するためです。辞書と設定は常にディスクから読みます
- **結果を値で返す**: 「検査した（診断の一覧）」「構文エラー」「検査しなかった（`exclude` に一致する、どのルールも適用されない、対応する言語がない）」「辞書がない」「辞書が不正」を区別した値を返します。文字列への整形や、同じ辞書の問題を 1 回だけ報告する処理は、呼び出し側が行います
- **CLI の振る舞いは変えない**: 切り出しの前後で出力と終了コードが変わらないことを、CLI の既存のテストで確かめます
- **公開する API**: `Project` は設定ファイルとそのディレクトリ（ルート）を表し、ルートからの相対パスへの変換（`relative`）、検査しないファイルの判定（`skip`）、ファイル探索（`walk`）を受け持ちます。`CheckRun` は、検査するソースの辞書を作成時にまとめて解決し、辞書のパスごとに `Checker` を使い回します。`CheckRun::check` はルートからの相対パスとテキストを受け取り、上の区別を `FileReport` で返します。辞書の編集は `edit_dictionary` が読み込み・`edit::apply`・書き込みをまとめて行います。M8 の MCP サーバの追加にあわせて、指定したパスから検査するファイルを選ぶ処理（`Project::select`）と、問題を 1 行の文字列にする処理（`report` モジュール）もここに置き、CLI と MCP サーバの出力をそろえています

あわせて、`check` で検査するファイルを指定できるようにします。エージェントの hooks や pre-commit から、編集したファイルだけを検査するためのものです（6.4 節）。

```sh
ubiqlint check src/main/java/com/example/order/domain/Order.java
```

- パスはファイルかディレクトリで、`--dictionary` と同じくカレントディレクトリからの相対パスか、絶対パスで指定します。設定ファイルのディレクトリの外を指すパスはエラーにして、残りのパスの検査は続けます。指定したパスがすべて外を指していても、ディレクトリ全体の検査に切り替えることはしません。パスを省略すると、従来どおり設定ファイルのディレクトリ以下をすべて検査します
- パスは、まず書かれたとおりに（`.` と `..` を取り除いて）比べます。それで設定ファイルのディレクトリの下になければ、シンボリックリンクを解決した実際のパスで比べます。一時ディレクトリのように、同じ場所が別の名前で見えている場合のためです
- ディレクトリを指定した場合は、従来と同じ規則（`.gitignore`・`exclude` など）でその下のファイルを探します。探索は設定ファイルのディレクトリから始めるので、そこから指定したディレクトリまでの間にある `.gitignore` も、全体を検査するときと同じく適用されます。探索のエラーは、指定したディレクトリの中と、そこへ至るディレクトリで起きたものだけを報告します。関係のない場所の壊れたリンクなどで、範囲を限った検査まで失敗しないようにするためです
- 直接指定したファイルが `exclude` に一致する場合や、対応する言語がない場合は検査せず、その旨を stderr に警告します。警告は終了コードに影響しません。`.gitignore` はファイルを探すときの規則なので、直接指定したファイルには適用せず、検査します
- 同じファイルを重複して指定しても 1 回だけ検査し、結果は全体を検査するときと同じくパスの順に出力します。違反を報告するパスも、全体を検査するときと同じく、設定ファイルのディレクトリにルートからの相対パスをつないだものです

### 6.2 MCP サーバ（M8）

エージェントには MCP サーバで、辞書とルールの取得、検査、辞書の編集を提供します。`ubiqlint mcp [--config <PATH>]` で stdio のサーバとして起動します。

```sh
claude mcp add ubiqlint -- ubiqlint mcp
```

| ツール | 入力 | 内容 |
|---|---|---|
| `get_context` | `path` | そのパスに適用される辞書のパスと内容、命名ルール（`target` とパターン、パターンが参照する語彙）、インポートルールを返す。`path` のファイルは存在しなくてよい |
| `check_code` | `path`, `content` | `content` を `path` に置いたものとして検査する。書き込む前の下書きを確かめるためのもので、`content` はファイル全体 |
| `check_files` | `paths`（省略可）, `limit`（省略可） | ディスク上のファイルを検査する。`paths` はファイルかディレクトリで、省略するとプロジェクト全体を検査する |
| `add_term` / `edit_term` / `remove_term` | `dictionary` と、`ubiqlint term` の各コマンドと同じ引数 | 3.2 節のコマンドと同じ編集を行う |
| `add_behavior` / `edit_behavior` / `remove_behavior` | `dictionary` と、`ubiqlint behavior` の各コマンドと同じ引数 | 同上 |

- **プロトコル**: MCP 2026-07-28 と、`initialize` で始まる 2025-11-25 以前の版の両方を受け付けます。旧来のクライアントは、新しい版しか話さないサーバにはつながらないためです。実装には公式の Rust SDK である `rmcp` を使い、版による違いは SDK に任せます。`rmcp` 3.x は Rust 1.88 以上を要求するので、ワークスペースの `rust-version` を 1.88 に上げます
- **状態を持たない**: ツールを呼ぶたびに設定を読み直し、`DictionaryResolver` も作り直します。ディスクの内容と食い違うことがなく、3.1 節の「編集後に再検査する呼び出し側は新しい resolver を作る」とも合います。キャッシュやファイルの監視は、必要になるまで入れません
- **設定ファイル**: 1 つのサーバが扱う設定ファイルは 1 つです。`--config` を省略すると、CLI と同じくカレントディレクトリの `ubiqlint.yaml` を使います。ファイルごとに最寄りの設定ファイルを探すことはしません（8 章）。設定ファイルが不正でもサーバは起動し、ツールの結果として設定の診断を返します。起動に失敗すると、エージェントからはツールがないようにしか見えないためです。クライアントがセッションを始める前に入力を閉じた場合（`server/discover` で確かめただけの場合など）は、正常な終了として扱います
- **パス**: 入力は絶対パスと、設定ファイルのディレクトリからの相対パスの両方を受け付け、そのディレクトリの外を指すパスは拒否します。出力は設定ファイルのディレクトリからの相対パスです。そのため、サーバは起動時に設定ファイルのディレクトリへ移動します。こうすると、違反メッセージに含まれる辞書のパスも同じ基準になります。範囲外のパスを報告するときだけ、設定ファイルのディレクトリを絶対パスで示します。MCP の Roots は 2026-07-28 で非推奨になったので使いません
- **出力**: 検査の結果は、CLI と同じ `path:line:column: error: message` の行で返し、最後に件数を添えます。CI のログと同じ見え方になり、JSON よりトークンも少なく済みます。`structuredContent` は使いません。`check_files` は、`limit`（既定は 100）件を超える違反を「ほか N 件」とまとめます。導入した直後に大量の違反が出ても、エージェントのコンテキストを使い切らないようにするためです
- **検査しなかったファイル**: `exclude` に一致する、どのルールも適用されない、対応する言語がない、といったファイルは、理由を付けて検査しなかったと返します。違反がないことと区別するためで、CLI の `warning: no source files were checked` と同じ考え方です。`check_files` では、どのルールも適用されないファイルを 1 つずつ警告の行で示し（`limit` 件まで）、最後の件数の「検査した」ファイルには含めません。ルールの `include` の指定漏れを、命名ルールに合っていると取り違えないようにするためです
- **ルートの辞書**: `check_files` は、CLI の `check` と同じく、設定ファイルのディレクトリにある辞書を検査対象のファイルが使うかどうかにかかわらず検証し、不正なら問題の行として 1 回だけ返します。MCP で通った変更が CI で失敗しないようにするためです。この検証は `Dictionaries::check_root` として CLI と共有しています
- **エラー**: 違反が見つかっても、ツールの呼び出しとしては成功です。呼び出し側が直すべき問題がある場合は `isError: true` にして、理由をすべて本文に書きます。具体的には次のとおりです
  - どのツールでも: 設定ファイルが読めない・不正、パスが範囲外、引数が不正（未知の引数を含む）
  - `get_context`・`check_code`: パスがディレクトリ、辞書が不正。`check_code` では辞書がない場合も、検査ができないのでエラーにします。`get_context` は、辞書がないことを通常の結果として伝えます
  - `check_files`: 範囲外のパスがある場合だけエラーにし、残りのパスの検査結果も一緒に返します。個々のファイルの読み込みエラーや、辞書がない・不正といった問題は、CLI と同じく問題の行として返します
  - 編集ツール: 編集が拒否された場合、`terms.yaml` 以外のファイルを指定した場合
- **辞書の編集**: `dictionary` は省略できず、設定ファイルのディレクトリ以下に既にある `terms.yaml` だけを受け付けます。辞書ファイルを新しく作らないのは 3.2 節と同じです。辞書の編集には設定ファイルの中身は要らないので、設定ファイルが不正でも編集はできます。引数は CLI と同じ規則（用語名、単語列、空でない文字列）で検証し、問題をすべてまとめて返します。編集には CLI と同じ `edit::apply` と書き込み処理を使い、結果の文言も CLI と同じです。同じサーバへの編集は 1 つずつ処理し、並列に呼ばれても変更が失われないようにします
- **ツールの並びと注釈**: `tools/list` は毎回同じ順序（ツール名の順。`rmcp` が名前で並べる）で返します。ツールの説明・引数のスキーマ・注釈はエージェントへの API そのものなので、CLI のテストでスナップショットとして固定します。注釈は次のとおりです。ローカルのファイルしか扱わないので、すべてのツールで `openWorldHint` を `false` にします

  | ツール | `readOnlyHint` | `destructiveHint` | `idempotentHint` |
  |---|---|---|---|
  | `get_context`、`check_code`、`check_files` | `true` | | |
  | `add_term`、`add_behavior` | `false` | `false`（追加だけ） | `true`（2 回目は重複として拒否され、辞書は変わらない） |
  | `edit_term`、`edit_behavior` | `false` | `true` | `true`（同じ値なら書き込まない） |
  | `remove_term`、`remove_behavior` | `false` | `true` | `true` |

- **サーバの説明（`instructions`）**: hooks のように検査を強制することはできないので、使い方の手順と禁止事項をここで伝えます
  - 型やメソッドに名前を付ける前に `get_context` を呼ぶ
  - ソースを編集したら `check_files` で検査する。書き込む前に確かめるなら `check_code` を使う
  - `terms.yaml` を直接編集せず、編集ツールを使う
  - 違反を消すためだけに用語や振る舞いを追加しない。辞書の変更はレビューで確かめられる

辞書を更新してよいかどうかは、人ではなく、レビューするエージェントが判断します。実装からレビューまでを AI エージェントが担う運用を想定しているためで、人の承認を挟む仕組みは設けません。ツールの実行も、クライアントの設定で一律に許可してかまいません。違反を消すためだけの更新（`Order` の振る舞いに `update` を足す、辞書にない同義語を用語にする、など）は、レビューするエージェントが `terms.yaml` の差分を見て止めます。ubiqlint が受け持つのは、辞書の変更を専用のツールに限って差分を小さく保つこと（3.2 節）と、レビューの観点を導入手順とあわせて文書にすること（[エージェントとの連携](agents.md)の 5 節）です。

### 6.3 LSP サーバ（M9）

エディタとエージェントには、LSP サーバで診断を届けます。Claude Code はプラグインで登録した LSP サーバから、ファイルを編集するたびに診断を受け取ります。hooks で作る予定だった「編集→違反→修正」のループを、特定のエージェントの仕組みに頼らずに作れます。ただし、Claude Code のクラウドセッションではプラグインの LSP サーバが起動しないので、そこでは MCP サーバだけを使います。

- **起動**: `ubiqlint lsp [--config <PATH>]`。`--config` を省略すると、クライアントが伝えるワークスペースのルートにある `ubiqlint.yaml` を使います
- **診断だけを扱う**: `didOpen`・`didChange` のたびに、バッファの内容とディスク上の設定・辞書で検査し、`publishDiagnostics` で送ります。同期は全文で行います。1 ファイルの検査は十分に速いので、変更のたびにその場で検査します。`didClose` で診断を消します。`terms.yaml` や `ubiqlint.yaml` が保存されたら、開いているファイルをすべて検査し直します
- **位置**: コアの列は文字単位で数えます（UTF-32 と同じ）。クライアントが `positionEncodings` で `utf-32` を受け付けるならそのまま使い、受け付けなければ行の内容から UTF-16 に換算します。単独の CR を改行とする扱いは LSP と同じです
- **診断の範囲とルール ID**: コアの `Diagnostic` に、識別子の範囲（`Name.span`）とルール ID を加え、LSP の `range` と `code` に使います
- **ライブラリ**: `lsp-server` と `lsp-types`。検査は同期処理で速いので、非同期のフレームワークは使いません
- **配布**: Claude Code のプラグイン（`ubiqlint lsp` を起動する `.lsp.json`）を用意し、ほかのエディタには設定方法を説明します
- **着手前の確認**: Java には公式の `jdtls-lsp` プラグインがあります。同じ `.java` に 2 つ目の LSP サーバを登録して、両方の診断が Claude Code に届くかを、実装の前に小さく試して確かめます

### 6.4 エージェントの hooks

特定のエージェントの hooks には、ubiqlint のコードでは対応しません。hooks はエージェントによって、イベント名、渡される入力、結果をモデルに返す方法が違います。Claude Code の形式を読めるエージェントもありますが、ツール名の違いなどがあり、互換は部分的です。なかでも、ubiqlint に必要な「編集の後に違反をモデルに返す」方法がエージェントによって最もばらつき、返せないものもあります。各エージェントの入力の形をコードに持ち込むと、エージェントの数だけ、変わり続ける仕様を追うことになります。

編集のたびに違反を届ける役割は LSP サーバ（6.3 節）に任せます。hooks から使いたい場合のために、ファイルを指定する `check`（6.1 節）を用意し、Claude Code の hooks の設定例と、ほかのエージェントの hooks からも同じように呼べるスクリプトを[エージェントとの連携](agents.md)に載せます。ほかのエージェントの設定例は、それぞれの公式の文書で形式を確かめてから加えます。hooks の形式はまだ変わり続けていて、確かめていない例を載せると、黙って動かない設定を広めるおそれがあるためです。

エージェントに `terms.yaml` を直接編集させないための設定も、文書で案内します。たとえば Claude Code では、hooks ではなく権限設定（`.claude/settings.json` の `permissions.deny`）で直接の編集を禁止できます。

## 8. 未決事項

- **`{verb}` と名詞の結びつけ**: 1 つの識別子に名詞が複数含まれる場合の規則。また、最も内側の型から名詞が得られない場合（匿名クラスや、名前に名詞を含まない入れ子の型など）に、さらに外側の型までたどるかどうか
- **enum 定数の対象**: enum 定数（`PLACED` など）は `field` として扱うが、通常のフィールドとは命名の慣習が違う。`target` を分ける必要があるかどうか
- **共有カーネル**: M5 では最も近い辞書だけを使う（3.1）。共有辞書を明示的に取り込み・合成する場合のスキーマと、重複・衝突の扱いは将来の拡張として未決
- **他言語のインポート表現**: 現在の `Import` は Java の別名なしインポートを表す。TypeScript の `import { Order as VendorOrder } from "@vendor/sdk"` や Python の `from vendor import Order as VendorOrder` のような別名インポートでは、インポート元の名前と導入されるローカル名を分けて保持する必要がある。また、TypeScript の `./order`・`@vendor/sdk` はドット区切りの識別子ではないため、`internal_namespaces` の書き方・検証・照合もそのまま使えない。次の言語を追加する前に公開型と設定スキーマの互換性を含めて設計する
- **用語を一部に含む外部型**: 構想 2.4 節の `Item` と `MenuItem` のような衝突も、インポート境界で扱うかどうか。M6 は用語名との完全一致だけを検査する。範囲を広げる場合は、`OrderDto` などの複合名との区別や、単語として含まれるかの判定方法も決める
- **同綴異義語**: `orderBy` や `sortOrder` のように、ドメイン用語と同じ綴りの一般語を含む識別子の扱い
- **米英の綴り**: `canceled` / `cancelled` のどちらを使うか、両方を許すか
- **出力形式**: CLI の出力として、テキストのほかに JSON や SARIF にも対応するか。MCP サーバは CLI と同じテキストを返す（6.2）
- **既存コードへの導入**: 既存の違反をまとめて抑制するベースラインの仕組み
- **辞書の作成とコンテキスト名の変更**: M7 のコマンドは既存の辞書の用語と振る舞いだけを編集する。辞書ファイルの新規作成や `context` の変更はコンテキストの境界に関わるので、コマンドで行えるようにするか、行えるとしたらエージェントに許すかは未決
- **辞書の同時編集**: コマンドは辞書を読んでから書き込むまでの間、ファイルをロックしない。その間に別のプロセスが辞書を変更すると、その変更は失われる。MCP サーバは同じサーバへの編集を 1 つずつ処理する（6.2）が、別のプロセスとの競合は防げない。複数のエージェントが同じ辞書を同時に編集する運用が出てきたら、書き込む直前の再確認やロックを検討する
- **複数の設定ファイル**: MCP サーバと LSP サーバは 1 つの設定ファイルだけを扱う（6.2、6.3）。モノレポで `ubiqlint.yaml` を複数置く場合に、ファイルごとに最寄りの設定ファイルを選ぶかどうか。選ぶなら、CLI の `check` が入れ子の設定ファイルの下をどう扱うかも合わせて決める
